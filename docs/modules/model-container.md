# 通用模型容器模块

契约设计版本 `0.1.0`。当前实现状态：**MiniMax-H3 专用参考实现**，不是已经完成的通用模型插件平台。这里的“容器”指具有身份、资源所有权和受控生命周期的模型运行单元；不把它限定为 Docker，也不把一个 Python 进程等同于操作系统资源隔离。

本模块回答：怎样让一次模型执行从接纳到产物、从失败到回收都能被外部查询与控制。模型质量目标由使用场景给定，容器不能用“进程退出码为零”代替用户目标达成。

## 四个视角与四类判断

“主观”标明目标或选择的提出者，不表示可以无视事实；“客观”要求可观察或可计算，也不表示观测没有误差。可选策略被部署选中后形成该实例的执行约束，但不会因此变成普遍物理条件。

| 视角 | 主观抽象的需求 | 客观具象的条件 | 主观具象的可选策略 | 客观抽象的可选验证指标 |
| --- | --- | --- | --- | --- |
| 核心 | 使用者希望得到符合输入约定、精度约定且可交付的产物，并能判断失败发生在哪个阶段。 | 在当前 H3 实例，读取 GPU 型号、系统可用 RAM、磁盘、依赖版本与参数精度审计；权重下载、加载成功、工作线程存活分别可观测。当前主干是 BF16，官方声明的 FP32 层保留；A100 80GB 与高 RAM 是本次通过的配置。 | 为一个部署选择模型适配器、精度配置、CPU offload 方案和预加载资产；H3 已实现 resident/staged 路线与已知 Turbo 配置，通用适配器注册仍属设计目标。 | 在声明输入集合上统计“产物合约合格率”和分阶段耗时；两者都不自动代表语义质量或用户满意度。 |
| 交互 | 主调度器应能在模型加载、繁忙、失败和关闭时继续查询、取消或排空，不因推理阻塞控制。 | 私有控制接口绑定 loopback 和独立密钥；执行身份包含模型 `instance_id`、`job_id`、`attempt_id`。观察 `ready`、`accepting`、阶段、取消请求和清理结果；请求返回不等于效果已完成。 | 选择排空、在安全边界取消或显式强制停止；传输结果未知时按同一尝试身份核对。当前实现保留终态结果，待总管理持久化后才确认消费。 | 控制查询延迟、取消确认耗时、未知执行的核对成功率；均按状态和故障类别分层统计。 |
| 递归 | 一个模型任务可以由多个子阶段组成，组合后仍保持可停止、可解释、资源可回收。 | 当前执行图为 CPU 预处理 → 独占 GPU 推理与 CPU 交接 → CPU 编码/完整解码校验；不同任务可重叠。GPU 阶段也消耗主机 CPU；预算来自 affinity/cgroup/可用内存与磁盘观察，不能重复借出同一物理资源。 | 对有限子任务选择串行、预算内并行或阶段流水；选择子失败后取消兄弟任务还是保留已验证产物。未来复合模型须递归传递身份、截止时间与取消原因，不能无界创建子任务。 | 清理闭合率、GPU 租约重叠违规数、各阶段重叠占比；重叠占比提高本身不证明吞吐量更优。 |
| 表达 | 面板、API、日志与测试应对同一次执行作出一致且有范围的陈述。 | 实际配置只在 GPU 租约内应用后写入 `generation_options.effective`；排队时为 null。下载进度、阶段事件、模型子实例、产物 SHA、清理回执均有不同含义；进程观测失败时不能声称已退出。 | 选择状态字段投射、事件摘要、日志详略和历史保留策略；将不存在或失效的证据表达为未知/过期，使用通用字段时附模型专用扩展。 | 表达一致率、未知状态误判数、观测时效；不以日志行数或字段数量衡量可解释性。 |

## 不因指标可选而可省略的约束

1. **身份与所有权。** 只执行当前模型实例接纳的尝试；相同尝试的重放不可重复执行，身份相同而参数改变必须拒绝。子进程拥有者用 PID 与进程创建时间联合识别，避免 PID 重用。
2. **精度与能力。** 当前场景遵循 A100 原生 BF16 与官方 FP32 例外，不能静默换成量化权重。资源不足、依赖错误或配置恢复失败应撤销相应能力；下载完成不能直接置 `ready=true`。
3. **共享配置隔离。** 注意力后端和预加载 LoRA 只在独占 GPU 租约内切换，完成 CPU 交接和 CUDA 同步后恢复。恢复未确认时不把不确定配置交给下一任务。
4. **终态与资源。** 取消请求不是取消完成；局部产物清理不是进程退出；进程退出也不是云实例释放。无法确认的资源继续记在原所有者名下。
5. **产物提交。** H3 成功产物须通过约定的编码、尺寸、帧数、音视频完整解码和 SHA 校验；总管理先持久化结果，再允许模型丢弃终态记录。通用模型应替换为该模型适用的产物校验器，而不是强制所有模型输出 MP4。

这些是当前合约内的正确性义务。下面的统计指标可以按目标选择；不选择某个统计指标，并不解除相应义务。

## 0.4.0 条件基础与 0.5.0 当前策略

原有需求保持不变。当前 [model_container.py](../../runtime/minimax_h3/model_container.py) 在自己的锁内复验 `model.execute`，工作集预留由预算所有者仲裁；管理器允许发出邀约不代表模型已经接纳。各阶段另行核对身份、执行能力、前序成功、取消与租约，只有必要条件全部为 true 才开始。unknown/conflict 不授权；drain 关闭新接纳，已接纳任务仍可按有效能力排空。

`stage_completions` 只在阶段成功且完成事件持久化后建立。相应策略是分开保留“允许开始、实际完成、租约归还”的证据，不从最终成功倒推先前授权；未知/冲突引起的条件失败保持原失败类别，取消意图另记。等待资源和实际计算继续在模型控制锁外进行，维持按真实依赖和预算并行。

0.5.0 私有查询包含 `last_condition_gate`、尝试 `condition_gates` 和 `stage_completions`；当前公共主任务会在运行中按 job/attempt/model 及观测时效投射 `execution_condition_gates`、`stage_completions` 和 `cancellation_requested`，并以 `execution_observation` 区分当前快照、历史终态、过期和未知。单个决定还须匹配尝试身份、决策 ID 和不晚于该快照的决策时间；缺失或不匹配不借用其他尝试的通过记录。终态先由主账本持久化后 ack，模型清除结果或管理器恢复不会把历史终态变成当前执行许可。

0.4.0 的短实验有完整六租约十二端点，仍保留为固定历史窗口。当前 [PipelineBudget](../../runtime/minimax_h3/pipeline_scheduler.py)在独立预算世代的 SQLite 审计中先持久化租约端点，再更新占用；每个端点有连续序号、前序摘要和自身摘要。内存只保留有界尾部，`status` 的当前容量视图不复制完整历史，另由 `budget_audit` 读取最多 256 条的固定截止范围。日志写入失败不制造释放证据、不归还不确定占用，`lease_journal.complete=false` 显式阻止以缺失历史作通过。审计库在重启后可只读分析，不能恢复为新实例的执行权。

长会话缺段、身份错配、摘要冲突或最后释放未确认仍须返回 unknown/错误，不能由终结占用为零声称全程无超借。[容器门控测试](../../runtime/minimax_h3/test_model_condition_gates.py)、[阶段预算测试](../../runtime/minimax_h3/test_pipeline_scheduler.py)、[实时投射测试](../../runtime/minimax_h3/test_live_condition_projection.py)和[分页接口测试](../../runtime/minimax_h3/test_budget_audit_projection.py)覆盖这些各自命名的本地反例。查询成本另由[预算查询基准](../../research/benchmark_budget_queries.py)按历史长度测量；CPU 微测不能推出 A100 端到端加速、完整 UI/API/日志一致率或物理最优。

## 通用化边界与递归组合

拟议的通用适配器边界是 `describe → prepare → infer → materialize → validate → cleanup`，配套 `load/status/cancel/drain/unload`。这是接口设计，不是声称仓库已有该名称的稳定插件 API。当前 `pipeline_backend.py` 的 `prepare/infer/encode/cleanup` 与 `ModelContainer` 提供了专用实现映射，注入 backend 也用于测试，并非第三方插件分发机制。

输入、输出、允许精度和加速能力应属于模型 profile；生命周期、身份和预算属于容器合约。H3 的“至少一个图片或视频参考”“Turbo 5 个调度点对应 4 次评估”是 H3 profile 条件，不提升为所有模型的规则。

```mermaid
flowchart LR
  P[主尝试：身份、预算、截止时间] --> R[CPU 参考准备子事件]
  R --> G[独占 GPU 子事件]
  G --> H[同步并交接 CPU 所有权]
  H --> V[CPU 编码与验证子事件]
  V --> C[局部清理及终态保留]
  C --> A[总管理持久化并确认消费]
```

若子事件又含子事件，仍需遵循同一身份/取消/结果/清理约定；展开图必须有限且无循环依赖。父节点只有在所需子结果可验证、所有自有子生命周期收敛、预算可对账后才完成。共享 GPU 或内存池只在一个层级作实际扣账，其他层保存引用，避免把一张卡复制成多个容量。当前只实现固定三阶段及参考媒体子任务，未实现任意递归 DAG 执行器。

## 可选指标的测量合同

阈值是场景策略，公式是评价方法，样本是观察事实，三者分开记录。跨进程时钟未校准时不能直接相减得到延迟；原始样本不足、缺阶段事件或分母为零时返回 `unknown` 并说明缺口，不补零。

| 指标 ID | 定义、单位与分母 | 测量窗与适用范围 | 未知规则 | 阈值策略 |
| --- | --- | --- | --- | --- |
| `MC-CORE-ARTIFACT` | 产物合约合格率 = 验证通过且已提交的成功任务数 / 被声明成功的任务数；单位比例。语义质量另测。 | 固定代码/模型/profile 的封闭测试批次，记录每个成功任务及产物校验回执。 | 无成功任务或任一成功任务缺验证证据则 unknown，不能报 100%。 | 对声明成功的任务要求每项合约成立；统计目标应为 1，任何违例单独记失败，不以均值掩盖。 |
| `MC-INT-CONTROL-P95` | 私有 `status` 从发起到收到同实例响应的 p95；单位 ms；分母是窗口内有效请求样本，另报错误与超时数。 | 同一客户端单调时钟，分别测加载期、推理期、停止期；窗口与样本数随报告给出。 | 样本不足、时钟不可靠或只保留成功请求而丢弃失败计数则 unknown。 | 延迟预算由部署交互目标预先选择；不得将本次约 2 秒轮询间隔当作服务 p95。 |
| `MC-REC-CLEANUP` | 清理闭合率 = 已核对全部自有子事件、租约及临时文件的终态尝试数 / 应清理的终态尝试数；单位比例，另列残留资源数。 | 一个容器实例从启动到停止的完整生命周期；包含成功、失败和取消。 | 终态清单或所有者观察缺失时 unknown；操作系统查询失败不当成无进程。 | 关闭验收要求当前实例清理闭合且残留数为 0；等待中的资源明确未确认，不能用平均值放行。 |
| `MC-REC-GPU-OVERLAP` | 同一物理 GPU 租约同时有两个不同所有者的时间区间数；单位 count；检查范围为全部已记录 acquire/release 区间。 | 当前单 GPU 独占方案的一次实例；不是 GPU kernel 活跃率。 | 区间缺端点、身份或时间顺序不可信时 unknown。 | 当前独占方案要求 0；未来多租约方案必须另立资源隔离与容量合约，不能沿用此阈值。 |
| `MC-EXP-CONSISTENCY` | 相同实例/任务/尝试/事件版本的表达字段一致率 = 符合源事件语义的字段数 / 比较字段数；单位比例。基础字段为 requested/effective/phase/artifact/cleanup，0.4.0 对照增加条件回执、stage_completions 和 cancellation_requested。 | 每次观察声明实际冻结的字段集合后比较 API、面板投射和日志解释；不把新增字段追溯成旧样本已覆盖，不直接比较异步不同时刻。 | 来源版本无法绑定或字段缺失时 unknown，缺失计数另报。 | 当前合约字段要求逐项一致；可选显示字段的覆盖目标由面板策略设定。 |

## 0.2.0 历史研究观测与指标对应

独立于下述历史基线，[2026-11-15 研究结果](../research/2026-11-15-results.md)的封闭批次包含两项模型执行成功。[提交轨迹](../../evidence/research-2026-11-15/trace.json)与[客户端验收](../../evidence/research-2026-11-15/client-receipt.json)核对了这两项产物的长度、SHA 和完整音视频解码，因此 `MC-CORE-ARTIFACT` 可记录 **2/2**；这不评价内容语义质量或长期成功率。

[轨迹分析](../../evidence/research-2026-11-15/analysis.json)观察到两段 GPU 阶段不相交，[阶段时间线](../../evidence/research-2026-11-15/timeline.json)记录跨任务 CPU/GPU 重叠。但 `MC-REC-GPU-OVERLAP` 定义要求全部 acquire/release 租约边界，当时 stage 包围事件不完全覆盖这些边界，该历史观察仍为 unknown。局部 cleanup 回执及进程退出也未形成逐子资源、租约和临时文件的完整枚举，因此 `MC-REC-CLEANUP` 保留 unknown；三项主任务不等于三项模型尝试。该轮也没有私有 status p95 和含 UI 的同源表达指标样本。

## 0.4.0 新条件下的指标复核

[运行时条件实测](../research/2026-11-15-runtime-condition-results.md)另有两项新的模型尝试成功，一项任务在队列中取消、没有进入模型尝试。依据本轮[提交轨迹](../../evidence/runtime-conditions-2026-11-15/trace.json)及[客户端回执](../../evidence/runtime-conditions-2026-11-15/client-receipt.json)，两件成功产物的下载长度、SHA 与完整音视频解码吻合，`MC-CORE-ARTIFACT` 追加本窗口 **2/2**。历史两件与本轮两件不合并成一个无版本分母，语义质量仍不在此指标内。

[条件与租约分析](../../evidence/runtime-conditions-2026-11-15/condition-analysis.json)核对了同一模型/预算实例的六个阶段租约、十二个端点和终结账本，无截断。其中两个独占 GPU 租约具有完整获取/释放区间且不相交，故 `MC-REC-GPU-OVERLAP` 可追加本窗口 **0 次**，旧窗口的 unknown 不回写。这证明声明租约的互斥，不是 GPU 内核活跃率，也不覆盖其他资源池。

`MC-REC-CLEANUP` 本轮仍为 unknown：租约端点和最终进程退出已补齐，但逐子事件和所有临时文件的完整清单与残留核对还缺失。已知模型尝试分母为 2，不把队列取消算成第三个模型尝试；服务清理及平台释放各自有证据，也不能代替这一更严格指标。`MC-INT-CONTROL-P95` 仍缺私有查询的分阶段请求全集；`MC-EXP-CONSISTENCY` 尚无包含新增条件字段的 UI/API/日志冻结对照，均追加本轮 unknown 和具体缺口，不以一次公共回执查询填为通过。

## 历史证据与未实现部分

[2026-11-15 验收摘要](../../evidence/acceptance-2026-11-15.json)记录 A100 80GB 原生 BF16 的三条成功视频、两条取消和一条早期依赖失败；成功产物经网页下载、哈希和完整解码核对，最终服务及平台会话释放。该有限样本支持指定路径，不证明任意模型、所有输入、语义质量或性能最优。

源码与针对性测试：

- [模型容器](../../runtime/minimax_h3/model_container.py)、[容器测试](../../runtime/minimax_h3/test_model_container.py)：加载期查询、取消与清理、终态身份和产物验证。
- [阶段预算](../../runtime/minimax_h3/pipeline_scheduler.py)、[阶段测试](../../runtime/minimax_h3/test_pipeline_scheduler.py)：跨任务阶段重叠、单 GPU 租约、CPU 共享预算和清理失败保留所有权。
- [H3 执行后端](../../runtime/minimax_h3/pipeline_backend.py)、[后端测试](../../runtime/minimax_h3/test_pipeline_backend.py)、[生成选项](../../runtime/minimax_h3/generation_options.py)：请求/实际配置、适配器切换与恢复。
- [进程所有者](../../runtime/minimax_h3/process_owner.py)：进程世代与退出确认。

待实现的是稳定的第三方适配器注册与兼容版本协商、其他模型 profile、任意递归 DAG、OS 级强制资源隔离及多 GPU 执行。当前 RAM/磁盘预算是准入估算而非强制配额；带宽未完整标定；没有有效同输入 A/B 提速结论。机器可读副本见 [模块合同](../../knowledge/modules/model-container.json)。
