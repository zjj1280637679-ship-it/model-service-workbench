# 客观条件集合：充分搜索与验证

本文件定义 0.3.0 的条件集合设计与证据边界。验证工作在本地进行，不据此启动 GPU；既有 [A100 实验](2026-11-15-results.md)仍是特定实例的历史观察。本文件中的契约是实现及审查依据，具体可执行范围以对应源码和验证记录为准。

“条件充分”是相对于**明确目标、模型、身份、时间与执行边界**的判断。检索到很多资料、列出很多条件、通过很多测试，都不自动构成充分性。需要分别回答：目标到底是什么；在声明模型内哪些条件足以推出目标；这些条件是否有当前有效证据；执行时能否取得所需资源；执行后目标是否真实达成。

## 四类知识继续分开

| 类别 | 本轮记录什么 | 不允许的替换 |
| --- | --- | --- |
| 主观抽象的需求 | 希望解决的目标、可接受失败方式与适用场景 | “希望能生成”不能成为“能生成”的证据 |
| 客观具象的条件 | 当前实例、对象、版本和时间范围内可核对的事实及未知 | 配置值、策略承诺、历史成功不能冒充当前观测 |
| 主观具象的可选策略 | 检索范围、候选生成方式、资源分配、超时与回退选择 | 选定单 GPU 独占不等于世界天然只有一种调度方式 |
| 客观抽象的可选验证指标 | 条件覆盖、反例、证明状态、有效证据比例等可复核定义 | “零已发现反例”不等于“完整搜索无反例” |

用户要求原生 BF16 是本场景的约束；配置选择 BF16 是已选择的策略；运行中实际参数精度审计是观察。三者有关联，但来源不同。`policy` 和模型 `constraints` 必须作为假设或策略单独记录，不能因写进布尔模型就变成物理事实。策略是否已经选择、配置是否已应用，可以分别有观察证据；策略内容的合理性不是观测自动证明的。

## 先定义目标，再搜索条件

每个目标 Q 至少记录：目标 ID、命题定义、对象/实例/尝试身份、所需结果、有效时间、代码/契约版本、观察者、失败与未知的处理，以及当前模型不覆盖的因素。不得只用一个 `success` 同时表示以下事实。

| 判断 | 精确责任 | 不能据此推出 |
| --- | --- | --- |
| 必要条件 | 在声明模型内，Q 成立时该条件必须成立 | 该条件单独足以产生 Q |
| 充分条件集合 | 在声明模型内，满足此集合的可行世界都满足 Q | 当前集合有证据；未来任务必然完成 |
| `can_start` | 当前尝试可合法接纳/派发，且所需预算可在规定仲裁点取得 | 已开始、模型 ready、最终成功 |
| `ready` | 当前实例在观察范围内具备约定能力 | 某任务已完成；能力永不失效 |
| `completed` | 该事件有终态类别和约定结果证据 | 一定成功；自有资源已全部释放 |
| `cleanup` | 该所有者的资源已按契约归还并确认 | 云平台已停止分配该实例 |
| `released` | 平台对指定实例的分配已结束 | 任意先前产物已经保存或下载 |

例如，“本地 API 能接收合规任务”和“公网 API 可达”是不同目标，后者还涉及选定隧道及当前实例的端到端观察；两者都不以模型文件下载完成为天然前置条件。“某任务可进入 GPU 阶段”则需要该任务的真实前置结果、当前模型能力、策略允许及资源仲裁。条件集合须按目标变化，不能从视频模型下载完成直接推出公网已经可达。

`completed` 应保留 succeeded、failed、cancelled 等类别。长驻服务可以 ready 而尚未 completed；已失败的事件可以 completed 而 cleanup 未知。已终结尝试不能因资源重新空闲被重新视为 can_start，重试需要新的显式尝试身份。

## 有限模型中的非空充分性

设布尔变量集合为 V，模型约束为 C，目标为 Q，候选前提集合 S 的合取为 P。世界 w 是对 V 的一个完整布尔赋值；只讨论满足 C 的世界。`SAT(F)` 表示至少存在一个使 F 成立的世界。

```text
模型有效：                 SAT(C)
候选前提有可行见证：       SAT(C ∧ P)
候选前提足以推出目标：     UNSAT(C ∧ P ∧ ¬Q)

因此充分集合要求同时满足： SAT(C ∧ P) ∧ UNSAT(C ∧ P ∧ ¬Q)
```

第二项不能单独使用。若 P 与 C 矛盾，经典蕴含在空世界集上成立，但它没有任何可执行条件见证；应报告 `unsatisfiable_premise`，不能宣布找到充分条件。若 C 本身不可满足，应报告模型矛盾，停止据此给出正向证明。

必要条件 N 要求 `UNSAT(C ∧ Q ∧ ¬N)`，并同时核对 `SAT(C ∧ Q)`。否则不可达目标也会使任意 N 在逻辑上“必要”。目标在该模型中不可达，只能说明模型内不可达，不能在没有现实模型对应证明时宣布实际服务永远不可能实现它。

前置条件搜索**禁止把目标 Q 本身、它的同义改名、目标结果标签或经循环回推的派生值放进 P**。不能以“已经成功”为“可以开始”的充分条件，也不能通过 `A 依赖 Q，Q 又依赖 A` 得到无外部根证据的证明链。候选的定义/来源依赖图应无循环，且不能依赖待证明目标。目标达成后的直接观察仍可以用于结果验收，只是不能反过来冒充事前条件证明。

这不禁止由独立原始事实构成、在模型内恰好与 Q 等价的正确判据；来源依赖与逻辑等价是不同问题。拒绝的是把目标结果重新包装成它自己的证据，而不是拒绝真正充分且必要的前置判据。

C 的定义也要审查：如果 `C ⇒ Q` 已经成立，空条件集合在该模型内可能充分，但这是“目标已由模型预设”，不算发现了实际客观条件。若模型直接把所需结论写为公理或把待验证程序行为写为永真约束，搜索最多验证这套表达的内部逻辑，不能提供行为真实性证据。对状态定义作布尔展开可以检查守卫表达；它不证明服务执行会遵守该定义。

## 最小集合不只有一种含义

| 结果 | 意义 | 必须保留的证据 |
| --- | --- | --- |
| 一个充分集合 | 当前集合在模型内非空且无反例 | 一个 C∧P 可行见证，以及 C∧P∧¬Q 已完整判定为不可满足 |
| 包含意义下的最小集合 | 删除任一成员都会失去充分性 | 每次删除后的反例；合取候选在相同 C 下可据此排除更小真子集 |
| 条件数最少的集合 | 所有允许候选集合中，没有更少成员的充分集合 | 对所有更小集合的完整排除，或等价的严格最优证明 |
| 按代价最优的集合 | 依某个已声明成本函数最优 | 成本定义、约束、所有更优方案的排除；这是策略目标，不是自然充分性的定义 |

一个集合可以包含意义下最小，却不是条件数最少；条件最少也未必最便宜、最可靠或最好观测。多个互不包含的充分集合可以同时存在。应保留替代集合及适用前提，不能把首次搜索到的一组说成唯一条件。

若时间、世界数、候选数或内存预算用尽，应分别报告“已验证候选”“未验证候选”“搜索是否完整”“最小性是否已证”。已找到的完整证明可以保留；但只检查部分世界而未发现反例不能升级为充分，候选空间尚未遍历不能升级为全局最少。没有在预算内找到充分集合，也不证明不存在。

## 从候选生成到原子复验

### 1. 固定目标与搜索边界

冻结目标、变量定义、允许的候选谓词、模型约束、当前策略、版本与搜索预算。区分理论证明需要的假设、真实服务必须满足的条件以及暂不建模的因素。条件 ID 保持稳定，同名谓词定义变更必须换版本。

以四个视角生成检查问题：核心转换需要什么；交互双方身份与回执如何绑定；递归子事件怎样继承预算和清理义务；API、面板、日志如何表达同一事实。视角帮助发现遗漏，不是强制四层串行，也不是完备性定理。

### 2. 生成候选与来源检索

候选可来自运行源码中的实际守卫、数据和控制依赖、接口契约、资源所有权、失败分支、测试反例及真实事件。逐项记录候选为何可能必要/充分，不能仅凭相邻出现、成功轨迹中的相关性或文件下载次序构造因果边。

检索以问题为索引：谁拥有该事实，哪个版本定义它，哪里有执行/失败证据，哪个观察能反驳它。对代码行为优先定位当前执行源码与对应测试；对实际运行读取对应实例回执；对外部协议或硬件能力读取匹配版本的第一手资料。检索到的文本可能描述目标、建议、配置或历史结果，须先分类，不能统一塞入“客观条件”。

检索记录应有问题、查询范围、来源、版本/时间、支持或反对的命题、尚缺内容与停止原因。两个转载或同一生产者派生的日志不能当两份独立见证。没有找到证据不等于证据支持否定。所谓“充分搜索”至多指已完成明确候选/来源范围与反例类别的工作，不能指开放互联网或现实世界已被全称穷尽。

本项目已有的 [状态与依赖说明](../architecture.md)、[有限模型反例](../../research/check_bound_cases.py)、[真实轨迹](../../evidence/research-2026-11-15/trace.json)与[证据边界](../validation.md)属于不同来源层。有限模型的声明输入不是 GPU 观测；真实观察也不因覆盖一个实例而成为所有模型的规则。

### 3. 绑定证据、身份与时效

每条证据至少关联命题 ID/版本、对象身份、组件实例、任务/尝试（如适用）、资源池身份、观察值、单位、观察时间或顺序、时钟域、来源身份、采集方法、有效范围与失效规则。测量误差、缺失字段、来源相关性也应保留。源码哈希能关联字节，不能独立证明运行内存和事实真实性。

同一物理池必须归一身份，不能用 `gpu_a` 与 `gpu_b` 两个别名创造容量。任务、尝试、组件实例、平台实例各自独立，不能仅凭同端口、相似 URL 或相同文件名连接证据。历史 v0.2.0 观察可支持当时那次运行，不能直接成为本次 volatile ready 或 free-memory 的真值。

新鲜度门限由策略选择，并给出依据。TTL 内的观察也不保证从未变化；版本/epoch、状态更新和租约失效规则须共同参与判定。跨宿主时钟未校准时不能直接相减；不同时刻的不同状态不自动构成逻辑冲突。只有同一命题、对象和可比较有效区间内的相反见证才进入冲突处理。

### 4. 评价真、假、未知与冲突

对当前目标范围，先过滤不可归属、已失效和不可比较的证据，保留过滤原因。令 E+ 为合格的支持证据，E− 为合格的反对证据：

| 状态 | 证据情形 | 操作含义 |
| --- | --- | --- |
| 真 true | E+ 非空，E− 为空 | 当前范围内有支持；仍受时效和执行仲裁约束 |
| 假 false | E+ 为空，E− 非空 | 当前有明确反证；不能以“暂时没观测到”代替 |
| 未知 unknown | 两者均空或必要字段无法验证 | 需要补证或保留未确认；不能自动变成 false、0 或成功 |
| 冲突 conflict | E+ 与 E− 均非空 | 保留双方来源，检查身份、时效、语义与观察误差；不能任意挑一个 |

这四种状态描述**证据情况**，不是把有限布尔模型的二值世界直接改成四值物理世界。离线搜索仍枚举模型声明的布尔世界；运行时未知条件应保留所有尚未排除的可能世界，不能为了套入布尔求解器随意填真或假。

来源优先级、更新覆盖或冲突化解必须有预先声明的规则和可审计理由。“取最后一条”不总是正确：迟到旧实例、旧 epoch 或低可信来源可能更新得更晚。必需前提未知或冲突时不能据此发放能力；如果另一个已验证充分集合在当前证据下全部成立，可以按所选策略评估它，不能偷偷删掉原集合中的不利条件。

### 5. 用反例验证与精简

对每个 P 先找可行见证，再搜索 `C ∧ P ∧ ¬Q`。找到时保存完整反例赋值及违反的目标子句；它可以否定这组充分性。没有找到时必须同时说明搜索是否覆盖全部允许世界，或者是否有可核对的不可满足证明。

反例不只用于“补一条条件直到样例通过”。还应检查模型是否误删真实世界、是否把策略写成天然约束、是否混用资源身份、是否混淆结果与前置、是否遗漏未知与时间。若根据反例修改 C、Q 或候选空间，重新编号并保留旧反例；不能用收紧模型排除失败场景后声称现实缺陷已修复。

得到充分集合后再做最小性检查，记录每个被删除条件所恢复的反例。证明输出至少保留模型/目标/候选版本、约束身份、搜索范围与预算、可行见证、反例或排除证书、最小性类型、未覆盖范围和复核器版本。结论必须能够从同一输入重新计算。

### 6. 执行前原子复验与执行后验证

“规划时所有事实为真”与“动作提交时仍成立”之间存在竞争窗口。资源空闲的观察不是资源已经预留；排队未取消的观察也不保证取消与派发竞争已经决定。

在实际副作用的仲裁点，重新核对当前实例/尝试、状态版本、策略版本、证据有效性与终结标志；在同一受控提交范围内取得所需资源、记录意图/状态转换及归属回执。若版本变化、资源被占用或取消已获仲裁，旧证明不得继续使用，应重新评价或等待。不能先释放锁再把先前“资源可用”当作已拥有租约。

“原子”必须说明覆盖哪个状态域。单进程锁、数据库事务或一个资源管理器的原子预留，不自动覆盖公网、云平台或多个独立服务。没有实现跨域原子协议时，应使用各域身份、版本、保留/确认、超时和补偿，并保留未知；不能把一系列顺序 RPC 命名为全局原子操作。当前服务已有同任务取消/派发仲裁及阶段资源所有者，相关设计见 [主事件模块](../modules/event-orchestrator.md)，不能据此宣称所有外部条件可被锁住。

动作开始后，继续观察阶段进展、配置实际应用、产物与清理；条件失效需要按策略撤销能力、停止新接纳、取消或收敛。即使事前模型中的 `can_start` 已证，未来 OOM、服务故障、网络中断或产物不合格仍可能发生。最终成功必须由实际执行回执验证，不能由前置条件证书代签。

## 可执行验证应覆盖的反例类别

以下是 CPU/有限模型的设计验收矩阵，不是声称已经执行本轮 GPU 实验。

| 类别 | 输入特征 | 预期边界 |
| --- | --- | --- |
| 矛盾前提 | C∧P 无可行世界 | 拒绝空真充分性 |
| 矛盾模型 | C 无可行世界 | 报模型错误，停止正向结论 |
| 直接或间接自证 | Q、Q 的别名或依赖 Q 的谓词进入 P | 拒绝目标泄漏与循环来源 |
| 不充分集合 | 存在 C∧P∧¬Q | 返回具体反例，而不是只有失败布尔值 |
| 多组最小集合 | 不同互不包含的集合都可满足目标 | 保留替代解，区分包含最小与数量最少 |
| 预算截断 | 世界或候选尚未穷尽 | 完备性/最小性未知，不假报不存在或最优 |
| 过期、缺失与冲突 | 旧实例、失效 epoch、无单位、相反有效见证 | 各自报告，不能将其折叠为真或零 |
| 资源别名 | 两名称对应同一物理池 | 按实际池扣账，不创造容量 |
| 执行竞争 | 观察后资源被占用或取消先提交 | 原子复验阻止旧证明触发副作用 |
| 完成与释放混淆 | 产物完成但清理缺失，或服务退出但平台未释放 | 分别保持 completed / cleanup / released 的事实范围 |

同一个反例还应投射为条件表、布尔公式、状态图与 API/日志解释，核对是否改变了可启动、就绪或完成判断。表达等效性针对具体命题与输入类，不靠字符串一致或绘图相似来证明。

## 物理必要下界与经验条件不得合并

对相同工作范围，若资源容量上界和必要工作量已知，物理下界 L 给出 `实际耗时 ≥ L` 这样的必要约束。满足某个耗时预算 `T ≥ L` 并不是该任务能够在 T 内完成的充分条件；离散调度、存储驻留、带宽竞争、启动与同步等仍可能增加耗时。

已有[有限反例](../../evidence/research-2026-11-15/finite-model.json)中，资源/路径下界合并为 3 个模型 tick，但精确网格最短时间是 4。该反例说明下界未必可达，不提供现实 GPU 秒数。把同一 GPU 伪装为两个池会把模型最短时间从 4 错算成 2；模型约束的物理身份是推导的前提。

已有 [A100 微基准](../../evidence/research-2026-11-15/calibration.json)记录某类形状、软件和设备条件下达到过的速率。它不是未来所有负载的容量上界，也没有提供完整 H3 的 FLOPs/HBM 工作量。因此物理下界差距比继续未知；不能用经验速率反解工作量再自我验证，更不能把 BF16 矩阵峰值直接套给 CPU 编码、网络或官方 FP32 路径。详细区分见[物理与经验参照](physical-and-empirical-bounds.md)。

## 充分性的最终声明格式

可接受的结论是：“在模型 C、目标 Q、候选空间及预算范围下，P 有可行见证，并且完整检查的允许世界中没有 P 成立而 Q 不成立的反例；最小性属于某种已说明类型。当前实例中 P 的哪些成员有有效证据、哪些未知/冲突，另列。执行仲裁与最终运行结果分别验证。”

不可接受的结论包括：“条件列齐所以必然成功”“搜索很多来源所以全称完备”“模型内蕴含成立所以云服务一定完成”“一次真实运行支持所以以后相同标签都成立”。开放世界存在未建模因素，有限证明与实际实验只能在公开范围内相互约束、逐步补充；不能相互冒充或消除所有未知。
